## 1. 종합 판정

v0.1은 UX 원칙(§5)과 문구 규칙(§15)이 특히 좋다. "실제 상태만 표시", "근거를 가까이 배치", "결과보다 신뢰"는 이 제품의 핵심 가치를 정확히 짚었고, 그대로 유지한다.

문제는 **문서 내부의 자기 모순**과 **미결정 사항이 그대로 남은 채 개발 착수를 전제**한 부분이다. 이 상태로 코드를 시작하면 Phase 1의 정의가 사람마다 달라지고, 수용 기준(§24)을 만족시킬 수 없다.

## 2. 스코프 모순 (해소 완료)

같은 기능이 문서 안에서 다른 우선순위로 두 번 정의돼 있었다.

| 기능 | §26 출시 단계 | 화면 요구사항 | 수용 기준 | E2E(§23.3) | 조치 |
| --- | --- | --- | --- | --- | --- |
| 수정 요청 / Revision | Phase 2 | FE-100~107 **Must** | FAC-08 | 포함 | **Phase 2로 확정.** FE-100~107·FAC-08을 Phase 2 절로 이동 |
| PDF 생성·다운로드 | Phase 2 | FE-113~115 **Must** | FAC-09 | — | **Phase 2로 확정.** §10.10에서 PDF 항목 분리 |
| SSE 진행 상태 | Phase 2 | §17.2 Should | — | — | Phase 2 확정. MVP는 폴링 단일 경로 |

**MVP 확정 범위**: 로그인 → 프로젝트 생성 → 자료 업로드 → 자료 검토 → 생성 → 미리보기 → PPTX 다운로드 → 프로젝트 삭제.

§23.3 E2E 시나리오도 이에 맞춰 축소한다. 수정 요청·PDF 단계를 제거하고 다음으로 대체한다.

```text
로그인
→ 프로젝트 생성
→ 텍스트와 파일 업로드
→ 자료 검토(부족·충돌 확인)
→ 12장 PPTX 생성
→ 진행 상태 복원
→ 슬라이드 미리보기
→ 출처 확인
→ PPTX 다운로드
→ 프로젝트 삭제
```

## 3. 값이 비어 있어 구현 불가했던 요구사항 (수치 확정)

요구사항에 "표시한다"만 있고 표시할 값이 없으면 구현도 테스트도 불가능하다. 다음 값을 확정한다. 백엔드 PRD와 어긋나면 백엔드 값이 우선한다.

### 3.1 업로드 제한 (FE-039 보완)

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 파일 1개 최대 크기 | 50MB | 회사소개서 PDF·이미지 다수 포함 기준 |
| 이미지 파일 최대 크기 | 20MB | OCR 대상 |
| 프로젝트당 최대 파일 수 | 20개 | §5.1 조사 범위를 덮는 실용 상한 |
| 프로젝트당 총 용량 | 200MB | |
| 텍스트 자료 최대 길이 | 50,000자 | |
| 모바일 업로드 제한 | 데스크톱과 동일. 20MB 초과 시 Wi-Fi 권고 안내만 표시 | §28-5 확정 |

화면에는 `사용 중 34MB / 200MB · 파일 4개 / 20개` 형태로 남은 양을 함께 보여준다.

### 3.2 폴링 정책 (FE-070/071 보완)

v0.1은 "3초 간격"만 정의해 종료 조건이 없었다. 생성이 10분 걸리면 200회 요청이 나간다.

| 조건 | 값 |
| --- | --- |
| 기본 간격 | 3초 |
| 탭 비활성 시 | 15초 |
| 지수 백오프 | 60초 경과 후 5초, 5분 경과 후 10초 |
| 최대 대기 | 20분. 초과 시 폴링 중단 후 `상태 확인이 오래 걸립니다. 다시 확인` 버튼 표시 |
| 연속 실패 | 3회 실패 시 폴링 중단, 네트워크 오류 안내와 재시도 버튼 |
| 서버 429 응답 | `Retry-After` 헤더를 따르고, 없으면 30초 후 재시도 |

서버 작업은 계속 진행되므로 폴링 중단은 작업 취소가 아니라는 문구를 함께 표시한다.

### 3.3 오류 코드 카탈로그 (§18 신설)

§23.1은 "오류 코드별 복구 행동" 단위 테스트를 요구하지만, `code` 문자열 목록이 문서에 없어 테스트를 작성할 수 없었다. 최소 세트를 정의한다. 백엔드와 이 표를 단일 계약으로 공유한다.

| code | 사용자 문구 | 복구 행동 | retryable |
| --- | --- | --- | --- |
| `FILE_TOO_LARGE` | 파일이 50MB를 넘습니다 | 파일 나누기 안내 | 아니오 |
| `FILE_TYPE_UNSUPPORTED` | 지원하지 않는 형식입니다 | 지원 형식 목록 표시 | 아니오 |
| `FILE_ENCRYPTED` | 암호가 걸린 파일은 읽을 수 없습니다 | 암호 해제 후 재업로드 | 아니오 |
| `FILE_CORRUPTED` | 파일이 손상돼 읽지 못했습니다 | 다시 저장해 업로드 | 아니오 |
| `SCAN_FAILED` | 파일 검사에 실패했습니다 | 다시 시도 | 예 |
| `PARSE_FAILED` | 문서 내용을 읽지 못했습니다 | 다른 형식으로 저장해 업로드 | 아니오 |
| `OCR_UNAVAILABLE` | 이미지 문서를 읽는 기능이 지금 동작하지 않습니다 | 텍스트로 직접 입력 | 예 |
| `QUOTA_EXCEEDED` | 프로젝트 용량을 초과했습니다 | 기존 파일 삭제 | 아니오 |
| `INSUFFICIENT_EVIDENCE` | 자료가 부족해 생성할 수 없습니다 | 자료 추가 | 아니오 |
| `GENERATION_TIMEOUT` | 생성이 제한 시간을 넘겼습니다 | 다시 시도 | 예 |
| `AI_PROVIDER_ERROR` | 분석 서비스에 문제가 있습니다 | 잠시 후 다시 시도 | 예 |
| `VALIDATION_FAILED` | 만든 자료의 검수를 통과하지 못했습니다 | 다시 시도 또는 장수 줄이기 | 예 |
| `PDF_FONT_FAILED` | PDF에서 한글이 정상 표시되지 않아 파일을 제공하지 않습니다 | PPTX 사용 | 예 |
| `RATE_LIMITED` | 요청이 많습니다 | 대기 시간 표시 | 예 |

예상하지 못한 `code`는 §17.3에 따라 `확인 필요`로 표시하고 `request_id`를 노출한다.

### 3.4 멱등성 키 규칙 (FE-065 보완)

v0.1은 "생성 시 멱등성 키 생성"만 요구해 §18.2(오프라인 재확인)와 연결이 끊겼다.

- 키 형식: UUID v4
- 생성 시점: 생성 설정 화면 진입 시 1회
- 저장 위치: `sessionStorage`의 `idem:{projectId}:generate`
- 재사용 조건: 같은 프로젝트·같은 설정으로 재요청할 때 같은 키를 보낸다
- 폐기 시점: 요청이 2xx 또는 4xx로 확정 응답을 받은 직후
- 409 응답 시: 이미 진행 중인 작업으로 간주하고 새 작업을 만들지 않고 해당 작업 진행 화면으로 이동한다

## 4. 누락돼 추가한 요구사항

### 4.1 프롬프트 인젝션 방어의 프론트엔드 몫 (§19.1 보강)

§29 체크리스트에 "업로드 문서의 명령이 화면이나 정책을 바꾸지 않는가"가 있으나 대응 요구사항이 §19에 없었다. `AGENTS.md` §3의 첫 원칙과 직결되는 항목이므로 명시한다.

| ID | 요구사항 |
| --- | --- |
| SEC-001 | 업로드 문서에서 추출한 텍스트와 AI 생성 텍스트는 인용 블록으로만 렌더링하고, 링크·버튼·폼 등 실행 가능한 UI로 승격하지 않는다 |
| SEC-002 | 추출 텍스트 안의 URL은 자동 링크로 만들지 않는다. 도메인을 평문으로 보여주고 사용자가 명시적으로 열도록 한다 |
| SEC-003 | 추출 텍스트를 화면 문구·버튼 라벨·경고 제목 등 UI 문구 자리에 삽입하지 않는다 |
| SEC-004 | 원문 발췌는 최대 500자로 자르고, 제어문자와 비가시 문자(ZWSP·RTL override 등)를 제거한 뒤 표시한다 |
| SEC-005 | Markdown 렌더링은 허용 목록 기반으로 하고, `img` `iframe` `script` `style` `a[href]` 태그를 허용하지 않는다 |

### 4.2 문구 관리 구조 (i18n 대비)

Phase 3에 다국어가 있으나 문구 분리 규칙이 없어 하드코딩이 확정적이었다.

- 상태 Enum → 사용자 문구 매핑은 `src/lib/messages/status.ts` 한 파일에 모은다
- 오류 `code` → 문구 매핑은 `src/lib/messages/errors.ts` 한 파일에 모은다
- 이 두 파일 밖에서 상태·오류 문구를 문자열 리터럴로 쓰지 않는다
- 나머지 UI 문구는 MVP에서 컴포넌트 내부에 두되, 위 두 파일의 분리는 지금 강제한다

### 4.3 백엔드 계약 미확정 대응 (§17 보강)

§17.2에 `Must` API가 14개인데 전부 미확정 상태였다. 프론트엔드 착수가 백엔드에 묶이지 않도록 다음을 요구사항으로 넣는다.

| ID | 요구사항 |
| --- | --- |
| CONTRACT-001 | 백엔드 OpenAPI 스펙을 단일 소스로 두고 `openapi-typescript`로 타입을 생성한다. 손으로 쓴 응답 타입을 두지 않는다 |
| CONTRACT-002 | 스펙 확정 전에는 MSW 목 핸들러로 개발한다. 목 핸들러는 OpenAPI에서 생성한 타입을 그대로 사용한다 |
| CONTRACT-003 | 목 핸들러는 성공 경로만이 아니라 §3.3의 오류 코드와 §10.5의 충돌 상태를 모두 포함한다 |
| CONTRACT-004 | 실제 API 연결 후에도 목 핸들러를 유지해 컴포넌트 테스트와 E2E에 사용한다 |

### 4.4 동시 접근과 다중 탭

v0.1에 없던 항목이다.

| ID | 요구사항 |
| --- | --- |
| FE-201 | 같은 프로젝트를 두 탭에서 열고 양쪽에서 생성을 시작해도 작업이 하나만 만들어진다(§3.4 멱등성 키) |
| FE-202 | 다른 탭에서 자료를 삭제해 현재 화면 데이터가 낡으면, 다음 요청의 404·409를 감지해 목록을 다시 불러온다 |
| FE-203 | 삭제된 프로젝트를 보고 있으면 삭제 완료 안내와 함께 목록으로 보낸다 |

## 8. 디자인 시스템(§12) 별도 보강 필요

§12는 색 9개와 폰트 크기만 있어 토큰 체계라 부르기 어렵다. 그리고 `#F6F7F4` 오프화이트 배경 + 네이비 강조는 지금 도구형 SaaS의 기본값이라 이 제품의 성격을 담지 못한다.

이 제품의 핵심 가치는 **사실·해석·추정·시나리오의 구분**이다(AGENTS.md §3, PRD §5.6). 근거 등급을 색으로만 구분하면 §14 A11Y-009(색상 단독 구분 금지)에도 걸린다. 따라서 **등급을 구조로 표현하는 토큰 체계**를 별도 문서로 설계한다.

- 확인된 사실: 실선 좌측 경계 + 출처 수 배지
- 분석 해석: 파선 좌측 경계 + `해석` 라벨
- 추정·시나리오: 점선 좌측 경계 + 사선 배경 패턴 + 면책 문구
- 자료 부족: 채워지지 않은 자리 표시 + 추가 방법 안내

색은 이 구조를 보조하는 역할만 한다. 상세는 `docs/DESIGN.md`에서 다룬다.
